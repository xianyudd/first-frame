🗑 其中 3 处要「先删掉」再写

上面六步里，②③④ 是在原来的行上补东西、改数值；另外 3 处不一样 —— 老师故意留了「临时写法」，让游戏在没做完的时候也能跑起来。你要先整行删掉，再写新的。删代码容易手抖，先把这 5 行认清楚（代码里都标了 ★TODO，照序号找）：

// ① 在 DrawGame 里 —— 删掉这两行方块：
DrawRectangleRec(player.rect, BLUE);
DrawRectangleRec(bullets[i].rect, BLACK);
// ⑤ 也在 DrawGame 里 —— 删掉这行红方块：
DrawRectangleRec(enemies[i].rect, RED);
// ⑥ 在 HandleHits 里 —— 删掉这两行「临时」码：
enemies[j].active = false;   // 临时：一下就死
score += 10;                 // 临时：不管什么怪都只给 10 分

删掉之后换成什么，每一步里都写好了：① 换成贴图 · ⑤ 按种类换贴图 · ⑥ 换成扣血。

⚠️ 别只删不补删掉一行、还没写上新的一行时，make 不会报错 —— 但会出怪事：⑤ 那行删了不补，下面画 HP / 分数的语句就被 if (enemies[i].active) 吃掉了，场上没怪时，分数那行字整个消失。每删一行就立刻补上一行，别停在「删完了」的中间状态。
📏 一条铁律写一个 → 编译 → 测试 / 试玩 → 通过 → 提交 → 再写下一个。一次只处理一个 ★TODO，顺着 ①→⑥ 做最顺（后面几步都要用到 ② 那张表）。

📦 贴图怎么画：一句 DrawSprite

老师已经把所有贴图放进 assets/，并写好了一个「门面」assets.h。你不用碰读图、缩放这些细节，只要一句：

DrawSprite(SpriteId::Player, player.rect);   // 在 player.rect 这个方框里，画玩家贴图

SpriteId 是「贴图名字表」：Player / Bullet / Grunt / Runner / Heavy / Elite / Floor。想画哪张，就把名字填进去。配置表里也存了每种怪该用哪张贴图。

看懂 make test 的红和绿

它是个自动评分器（autograder），按可测的 TODO 分组打分：

[2] Config table -- four enemy kinds' stats
  [PASS] Runner faster than Grunt (speed)
  [FAIL] Heavy hp > 1 (takes several hits) (test_todos.cpp:73)
   -- group passed 5 / 6 --
  • 🟢 [PASS] = 正确；🔴 [FAIL] = 有误，读那行英文说明。
  • 有的行还会给 (expected X, got Y)（期望 X、实际 Y），直接点出差在哪。
  • 行尾 (test_todos.cpp:73) 是检查所在行号。
🔤 为什么是英文评测输出特意用英文（[PASS]/[FAIL] + 组名 [2] [3] [4] [6]），这样在任何终端里都绝不乱码。组号 [2]…[6] 就对应下面 TODO 的 ②…⑥。
⚠️ 注意功能测试覆盖 ②③④⑥；画面类 ① 玩家/子弹贴图 和 ⑤ 敌人贴图 只检查绘制源码，不能证明贴图外观，仍要用眼睛验——make run 跑起来，四种怪长相不同、玩家子弹是贴图，就算过。

提交三步（commit）

git add src/main.cpp       # ② 放进「待提交」区
git commit                 # ③ 正式提交（照弹出的模板填标题）

2填全配置表 📊

这一步是全课的核心。在 ConfigOf 里，照「普通怪」的范例，补上快速 / 重甲 / 精英三行数据。

⏱ 预计 25 分钟🧩 前置：① 完成📄 改 ConfigOf🧪 可自动测

🎯 这一步学会

  • enum class：给每种怪起个名字（类型）
  • struct + switch：一种怪对应「一行数据」
  • 数据驱动：强弱写在表里，不写死在逻辑里

📖 概念：类型 + 配置表

enum class EnemyKind 给四种怪各起个名字（Grunt / Runner / Heavy / Elite）。EnemyConfig 是「一行数据」，装着一种怪的全部数值：{ 贴图, 速度, 满血, 分数, 大小 }。ConfigOf(kind) 就是查表——给一个种类，返回它那一行。以后想让重甲更肉？只改表里那个血量，别处一个字都不用动。这就叫「数据驱动」。

📋 你要做到

范例已给：case EnemyKind::Grunt: return { SpriteId::Grunt, 1.8f, 1, 10, 40 };。照它补三行，让四种怪满足这些关系（具体数字你自己定）：

种类性格（要满足的关系）
快速 Runner比普通快、很脆（1 血）、分数略高一点
重甲 Heavy比普通慢、肉（血量 > 1，建议 3）、分数更高
精英 Elite血量最高（建议 6）、够猛、分数最高（压轴）

每种怪的贴图别填错、别填重：Runner 用 SpriteId::Runner，Heavy 用 SpriteId::Heavy，Elite 用 SpriteId::Elite。

🎯 这一步学会

★挑战项目：会绕墙追人的怪（BFS 最短路）🧠

前面 6 步是必做地板。这一关没有标准答案、也不自动评分——它把你在算法里学的 BFS 搬进游戏：让怪不再直线撞墙，而是绕开墙、走最短路抓你。make run 跑起来能看见怪绕过障碍，就算成功。

🎯 你要做出什么

在场地上放几堵墙，让某一种怪（建议先拿 EnemyKind::Elite）用 BFS 单源最短路朝玩家逼近：一格一格绕过墙，而不是穿墙或卡在墙上。

📖 概念：网格 + BFS 单源最短路

你们的地板本来就是 TILE = 40 的网格，正好当 BFS 的格子：整块场地是 SCREEN_W/TILE × SCREEN_H/TILE = 32 × 18 格。把某些格标成墙，其余能走。BFS 从玩家所在格出发一圈圈往外扩，天然算出每一格到玩家的最短步数——这就是「无权图最短路只能用 BFS、不能用 DFS」的原因。

📋 你要做到（四步）

  1. 建网格：一个 bool wall[18][32] 标出哪些格是墙（先手动摆一个 L 形试试）。
  2. 单源 BFS：从玩家格 (player.rect.x/TILE, player.rect.y/TILE) 出发，用 queue + int dist[18][32]，算出每格到玩家的最短步数（墙不入队）。
  3. 怪查表走一步：怪看自己四个邻格里 dist 最小的那格，朝它走——那就是最短路的下一步。
  4. 一次 BFS 喂全部怪：一遍 BFS 覆盖全图，所有寻路怪查同一张 dist 表；玩家没换格就复用，或每 N 帧重算一次。

🧠 讲究在哪（GESP 想深一层）

  • 为什么 BFS 不是 DFS：无权图里 BFS 第一次到达某格就是最短，DFS 不保证。
  • 为什么从玩家单源出发而不是每只怪各跑一次：一次 BFS 是 O(格子数)=O(32×18)，几十只怪就省几十倍——这叫「共享计算」；那张 dist 表其实就是一张 flow field。
  • 复杂度取舍：每帧全图 BFS vs 缓存复用，正是真实游戏里的性能权衡。

💡 火花（选做，越挑越硬）

  • 哪些种类会寻路：给 EnemyConfig 加一个 bool smart，用配置表决定——又回到本课的「表驱动」。
  • A*：把 BFS 换成 priority_queue 按 dist + 曼哈顿距离 排序，更快找到路。
  • 让墙随关卡变化，或让玩家能放墙「骗」怪绕远。

🧪 怎么算成了

★这一格不自动评分——make run，把墙摆成 L 形：寻路怪会绕过去、普通直线怪会卡在墙上。两种一对比，你就亲眼看见 BFS 的价值了。做完给爸妈演示一下！

🛟 卡住了看这里

出现红色（未通过）很正常。程序员大多数时间都在「写一点 → 测试 → 发现问题 → 修改 → 再测试」。这就是 Debug，和写代码一样重要。

🔧 测试变红：按这个顺序查

  1. 哪一条失败？读那行英文说明和 (expected X, got Y)。
  2. 是哪一组？失败属于 ②③④⑥ 哪组，就只改那一步。
  3. 是不是漏做了前置？②→③→④/⑥ 是有依赖的（种类、满血、查表）。
  4. 改完 make test 再看一遍。

📋 常见症状对照表

症状多半是
make 报一堆红字漏了分号或括号没配对，某个 case 忘了 return —— 看第一条错误的行号
出现品红色方块贴图没加载：SpriteId 名字拼错，或 assets/ 里缺图
四种怪长得一模一样⑤ 还没改成 DrawSprite，或 ② 配置表 sprite 填重了
四种怪速度一样④ 还是写死 1.5f，没查表；或 ③ 没记 kind
重甲一枪就死③ 没设 cfg.maxHp（开场只有 1 血），或 ⑥ 没改扣血
分数不管什么怪都 +10⑥ 加分没用 ConfigOf(kind).score，还写死 10
HP / 分数那行字时有时无⑤ 的红方块只删了、还没补 DrawSprite —— 画字的语句被 if (enemies[i].active) 吃掉了，没怪时就不画（见 0 · 三处要删的）
git commit 说 nothing to commit没 git add，或文件没真改动 —— 先 git status
🤖 一句话全绿 ≠ 一定完美，但出现红色 = 一定有问题。画面类的 ①⑤ 仅检查绘制源码，无法验证最终外观，务必 make run 亲眼看一遍。

★通关验收

六步都做完了？从干净状态重头跑一遍：

make clean && make && make test && make run

✅ 逐条对照

✅ 玩家、子弹是贴图        ✅ 四种怪长相各不相同
✅ 快速怪明显更快          ✅ 重甲慢吞吞、要连打几下才倒
✅ 精英最肉、给分最多      ✅ 杀不同的怪加不同的分

判定：make test 里 ②③④⑥ 全绿 + 眼睛看 ①⑤ 对。两个都满足，通关 🏆。

enum class（给东西分类型）· struct（打包一组数据）· 配置表 / 查表（数据驱动：强弱写在表里）· switch · 贴图绘制 DrawSprite。还有一个能受用很久的思路：想改平衡，只改一张表，逻辑一行不动——后面几课的道具、掉落都会复用它。
